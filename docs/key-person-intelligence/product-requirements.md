# 关键人物动态模块：产品需求规格（PRD / SRS）

状态：Draft 0.1
产品范围：家庭工作台 / AI 情报 / 关键人物动态
目标版本：MVP

## 1. 背景与问题陈述

用户当前需要分别访问社交平台、采访视频、公司官网、监管披露和媒体报道，才能了解科技领袖、
投资人、政策人物及相关机构的最新动向。信息分散、重复、来源质量不一，且普通新闻摘要很少回答：

1. 这个人或机构实际做了什么、说了什么？
2. 与其过去的观点或行为相比，有没有发生变化？
3. 这件事为什么值得关注，证据来自哪里？
4. 它与家庭关注的公司、行业或投资主题有什么关系？

本模块的目标不是建立“全网新闻搬运站”，而是形成一个**以关注对象为主线、以证据为底座、
以变化识别为价值核心**的个人情报工作台。

## 2. 产品目标

### 2.1 MVP 目标

- 集中管理需要持续关注的人物和机构。
- 从合规、可核查的信息源收集动态，并保留原始链接和时间。
- 将多篇重复报道聚合为一个“情报事件”。
- 使用 AI 生成中文结构化摘要，明确区分事实、观点、推断和未知项。
- 识别同一关注对象观点、立场、投资行为或经营动作的变化。
- 提供今日动态、人物时间线、事件详情和运行状态页面。
- 适配现有 Django、PostgreSQL、家庭成员权限和群晖 NAS 部署方式。

### 2.2 非目标

- 不提供自动交易、买卖建议或收益承诺。
- 不将单条社交平台发言直接解释为确定的投资结论。
- 不绕过平台登录、验证码、反爬措施或付费墙。
- 不在 MVP 中建设实时流处理、Celery、Redis 或独立微服务。
- 不在本阶段同步开发个股行业新闻和 AI 前沿频道。

## 3. 核心产品原则

1. **证据优先**：所有 AI 结论必须能回到一个或多个来源条目。
2. **事件优先**：同一事件的多篇报道应聚合，不重复轰炸用户。
3. **变化优先**：突出“相比过去发生了什么变化”，而非仅复述新闻。
4. **来源分级**：官方原始材料优先，二手报道用于发现和补充背景。
5. **人机分工**：采集、归类和初步摘要自动化；高影响、低置信度内容允许人工复核。
6. **可降级**：AI 或单一信息源不可用时，仍能展示原始条目和失败状态。
7. **少而重要**：默认信息流按重要性和新颖度排序，而不是按采集数量排序。

## 4. 领域术语

| 术语 | 定义 |
|---|---|
| 关注主题（Subject / Topic） | 被跟踪的人物、机构、行业、技术、政策或证券。为兼容 M1，代码模型暂保留 `Subject` 名称。 |
| 信源（Source） | 官网、RSS、社交账号、视频频道、监管披露或可信媒体入口；可关联多个关注主题。 |
| 来源条目（Source Item） | 从单一信息源取得的一篇文章、一条帖子、一段采访、一个视频或一份披露。 |
| 情报事件（Event） | 对同一现实事件的归并结果，可由多个来源条目共同支撑。 |
| 证据（Evidence） | 支撑某项事实或观点的来源链接、短摘录、时间和发布者。 |
| 变化信号（Change Signal） | 相比历史立场、行为或预期出现的可解释变化。 |
| 每日简报（Digest） | 指定时间窗内按重要性精选的情报事件集合。 |

## 5. 用户角色

沿用家庭工作台的成员模型：

- `admin`：管理关注主题、信源、采集任务和人工复核。
- `member`：查看动态、关注/取消关注、收藏、标记已读；是否允许新增来源在 MVP 设计冻结时确认。
- `viewer`：只读查看，不能修改关注和事件状态。

系统仍按当前“单家庭”架构运行，不新增第二套身份系统。

## 6. 建议的首批关注对象

以下作为初始化候选，不在数据库迁移中硬编码，可通过管理命令或后台配置：

| 类别 | 候选对象 |
|---|---|
| 科技领袖 | 马斯克、黄仁勋、Sam Altman |
| 投资人 | Warren Buffett、Ray Dalio、Michael Burry、Cathie Wood |
| 政策人物 | Donald Trump |
| 相关机构 | Berkshire Hathaway、ARK Invest、OpenAI、NVIDIA、Tesla/SpaceX |

人物与机构需要建立关系，例如“Warren Buffett — Berkshire Hathaway”“黄仁勋 — NVIDIA”，
但二者分别保留独立时间线和来源。

## 7. 核心用户场景

### 场景 A：查看今日重要动态

用户进入模块首页，看到过去 24 小时最重要的事件。每张卡片展示：关注对象、发生了什么、
为什么重要、发布时间、来源数量、置信度和原文入口。

### 场景 B：追踪某人的观点变化

用户打开人物详情，按时间查看发言、采访、投资动作和经营决策。系统对可比较事件显示：
“延续原观点”“语气增强”“观点转向”或“证据不足”。

### 场景 C：核查 AI 摘要

用户从事件详情查看事实列表、AI 解读、短证据和原始链接。AI 不能引用到来源的陈述应标记为
“推断”，不能伪装成事实。

### 场景 D：信息源或 AI 失败

管理员在网页运行状态中看到失败源、错误摘要、最近成功时间和重试结果；失败不得让整个首页报错。

## 8. 功能需求

### 8.1 关注主题与关系

| 编号 | 需求 |
|---|---|
| KP-FR-001 | 管理员可以新增、编辑、停用人物、机构、行业、技术、政策、证券或通用主题。 |
| KP-FR-002 | 每个关注主题包含中英文名、别名、类别、简介、头像链接和重要性等级。 |
| KP-FR-003 | 可以记录人物与公司/机构之间的任职、创办、投资或关联关系。 |
| KP-FR-004 | 家庭成员可以关注或取消关注主题；系统保留全局主题但按关注关系生成家庭视图。 |

### 8.2 信息源管理

| 编号 | 需求 |
|---|---|
| KP-FR-010 | 关注主题与信源为多对多关系：一个主题可有多个信源，一个信源也可关联多个主题。 |
| KP-FR-011 | 信源记录类型、URL/外部 ID、来源等级、类别、采集适配器、采集周期和启停状态。 |
| KP-FR-012 | 管理员可以在信源地图查看活跃、异常、到期待抓取、平台分布、最近成功和连续失败次数。 |
| KP-FR-013 | 支持人工提交原文链接或手工事件，作为不可自动采集平台的安全降级入口。 |
| KP-FR-014 | API Key 只从环境变量读取，不写入数据库、页面或日志。 |

### 8.3 采集与标准化

| 编号 | 需求 |
|---|---|
| KP-FR-020 | 采集任务由 Django 管理命令运行，并支持按来源、对象、时间窗和数量限制执行。 |
| KP-FR-021 | 同一来源条目重复采集时幂等更新，不产生重复记录。 |
| KP-FR-022 | 保存标题、发布者、发布时间、规范化 URL、短摘要/短摘录、外部 ID 和内容指纹。 |
| KP-FR-023 | 采集失败记录到运行日志，并返回非零退出状态供 DSM Task Scheduler 告警。 |
| KP-FR-024 | 不默认保存受版权保护的完整正文；仅保存处理所需的最小内容和来源证据。 |

### 8.4 事件聚合与去重

| 编号 | 需求 |
|---|---|
| KP-FR-030 | 规范化 URL、外部 ID 和内容指纹用于确定性去重。 |
| KP-FR-031 | 标题、对象、时间窗和语义相似度用于候选事件聚类。 |
| KP-FR-032 | 多个来源条目可以归入一个情报事件；管理员可以拆分或合并错误聚类。 |
| KP-FR-033 | 同一事件新增权威来源时更新证据和置信度，而不是再次推送为新事件。 |
| KP-FR-034 | 系统使用版本化代码策略计算重要性和置信度，并保存全部特征、权重和计算明细。 |
| KP-FR-035 | 事件分为今日精选、全部动态、待复核和噪音箱；噪音仍保留最小原始记录。 |

### 8.5 AI 分析

| 编号 | 需求 |
|---|---|
| KP-FR-040 | AI 输出必须符合版本化 JSON Schema，不接受无法解析的自由文本作为正式结果。 |
| KP-FR-041 | 输出字段至少包含：一句话摘要、事实、观点、关键数字、事件类型、重要性、置信度和不确定项。 |
| KP-FR-042 | 有足够历史证据时生成变化信号；证据不足时明确返回“无法判断”。 |
| KP-FR-043 | 每项事实或观点都关联来源条目；无法关联的内容只能作为推断。 |
| KP-FR-044 | 保存模型、服务商、提示词版本、处理时间和失败原因，支持后续重跑。 |
| KP-FR-045 | AI 失败不删除来源条目，页面降级显示原始标题、来源和链接。 |
| KP-FR-046 | 低成本相关性门控先过滤明显无关条目，高成本分析只处理通过门控的候选。 |
| KP-FR-047 | AI 只输出独立特征和证据判断；最终权重、阈值和精选结果由版本化代码策略计算。 |

### 8.6 页面与交互

| 编号 | 需求 |
|---|---|
| KP-FR-050 | 首页为“今日精选”，只展示达到重要性与置信度阈值的事件。 |
| KP-FR-051 | 支持按人物/机构、类别、事件类型、来源等级、重要性和时间筛选。 |
| KP-FR-052 | 关注主题详情提供时间线、来源列表、历史主题和变化信号。 |
| KP-FR-053 | 事件详情展示摘要、为什么重要、事实/观点区分、全部证据、原文链接和处理元数据。 |
| KP-FR-054 | 用户可以标记已读、收藏和静音；MVP 可先完成已读与收藏。 |
| KP-FR-055 | 管理员具有信源地图和五段流水线页面，不把所有运维能力只放在 Django Admin。 |

### 8.7 每日简报

| 编号 | 需求 |
|---|---|
| KP-FR-060 | 系统可为指定日期生成一次幂等的每日简报。 |
| KP-FR-061 | 简报按重要性、新颖度、证据质量和用户关注关系选取事件。 |
| KP-FR-062 | 网页展示简报；外部消息推送不属于 MVP，但数据模型预留投递记录。 |
| KP-FR-063 | 每日简报复用已处理事件进行分桶和排序，不为生成日报重复调用 AI。 |

### 8.8 反馈与评估

| 编号 | 需求 |
|---|---|
| KP-FR-070 | 管理员可以标注误选、漏选、重复聚类、主来源错误和变化标签错误。 |
| KP-FR-071 | 评分策略升级前必须在冻结历史样本上回放，并保存新旧版本差异。 |
| KP-FR-072 | 用户反馈不直接在线修改 Prompt、权重或阈值，只作为离线评估样本。 |

## 9. 页面信息架构

```text
AI 情报
└── 关键人物动态
    ├── 今日精选
    ├── 全部动态
    ├── 信源管理
    ├── 关注主题
    │   └── 主题详情 / 时间线
    ├── 流水线（管理员）
    ├── 收藏
    └── 运行状态（管理员）
        ├── 采集运行
        └── 待复核事件
```

事件卡片建议固定展示：

- 关注对象与事件类型
- 一句话事实摘要
- “为什么重要”一句话
- 发布时间与最近更新时间
- 来源等级与来源数量
- 重要性分数、AI 置信度
- 变化标签：新动向 / 延续 / 增强 / 转向 / 无法判断

## 10. 非功能需求

| 编号 | 要求 |
|---|---|
| KP-NFR-001 | 首页 GET 请求不得触发外部抓取、AI 调用或隐式数据库批量写入。 |
| KP-NFR-002 | 采集和简报命令必须幂等，可安全重跑。 |
| KP-NFR-003 | 单一来源失败不影响其他来源处理；运行记录可审计。 |
| KP-NFR-004 | API 请求设置超时、限速、重试上限和明确 User-Agent。 |
| KP-NFR-005 | 数据按家庭成员权限展示；`viewer` 角色只读。 |
| KP-NFR-006 | 所有时间以带时区时间保存，页面按站点时区显示。 |
| KP-NFR-007 | 桌面和手机宽度均可使用，重要字段不依赖悬停才能查看。 |
| KP-NFR-008 | 模型或来源升级不得覆盖历史处理元数据。 |

## 11. MVP 验收标准

满足以下条件才视为第一版完成：

1. 至少配置 5 个关注对象、每个对象至少 1 个可用来源。
2. RSS/官方页面、YouTube 或人工录入中至少两类适配器通过真实样本验证。
3. 同一条目重复运行三次只保留一条记录。
4. 两个来源报道同一事件时可聚合，并同时保留两个原文链接。
5. AI 摘要中的事实能够逐项追溯到来源；AI 不可用时页面仍可用。
6. 首页、对象时间线、事件详情和管理员运行状态页面通过权限与响应式测试。
7. 采集、处理、每日简报命令均有运行记录，失败返回非零状态。
8. 全项目测试通过，迁移可在空库和已有库上执行。
9. NAS 部署前完成数据库备份；部署不覆盖生产数据库、媒体文件或 `.env`。

## 12. 待确认产品决策

以下不阻塞文档设计，但在进入 AI 和自动采集阶段前需要确认：

1. 第一批正式关注对象是否采用第 6 节候选名单。
2. “关键人物动态”默认对全体家庭成员可见，还是允许成员拥有私有关注列表。
3. 首版是否优先接入 X API，还是先用官网/RSS、YouTube、SEC 与人工录入验证价值。
4. 每日简报希望在北京时间几点生成。
5. 首版人工评估集由多少条历史样本起步，以及由谁确认“应该精选/不应该精选”。
